## Six-point magic circle — actual renderer failure

### Existing production renderer path

`phaser-field.js` renders large floor effects as multiple horizontal images so each band can have the depth of its own map row:

- floor: `row * 100`
- floor effect: `row * 100 + 46`
- wall / wall face: `row * 100 + 48 / +49`
- player/actors: around `row * 100 + 88`

That depth design is correct for the requested ordering:

`floor -> magic circle -> walls/actors`

The problem was in the scaling after `setCrop()`.

### Old behavior

The source image is 384x384. The 9-tile effect is split into 9 horizontal crops of roughly 42–43px each.

The old code then called:

```js
image.setCrop(0, cropY, sourceWidth, cropHeight);
image.setDisplaySize(displayWidth, TILE_SIZE * sliceTiles);
```

Phaser's `setDisplaySize()` still derives its scale from the original frame dimensions, not from the crop rectangle.

For a 384px-high source and a requested 32px row:

- Y scale becomes `32 / 384 = 0.08333...`
- a 42–43px crop is actually displayed at only about 3.5px high
- 9 strips reconstruct only about 32px of visible content inside a 288px-tall layout

The strips are separated by the intended 32px row spacing, so almost the entire magic circle is transparent gaps. This explains why the renderer reported no error while the effect looked absent.

It also explains the earlier observation that the 4-tile version was visible: four 96px crops become about 8px high each. That was already wrong, but enough of the image remained visible to notice it. The 9-way split reduced visible vertical coverage from about 25% to about 11%.

### Phase 20 fix

The crop rectangle itself now determines the Y scale:

```js
const targetSliceHeight = TILE_SIZE * sliceTiles;
image.setScale(
    displayWidth / sourceWidth,
    targetSliceHeight / cropHeight
);
```

For the current 9x9 effect this reconstructs all 9 rows at 32px each: 288px of visible image across the 288px intended footprint.

The absolute position remains X17/Y16, and the per-row depth contract is unchanged.

This is not an error-suppression fix; it changes the actual pixels generated by the Phaser renderer.

## Abyss vortex lower-half clipping

The user's suspicion that the floor renderer was involved was correct here too.

`PLAY_EFFECT` previously rendered a large 4.2-tile image as one Phaser image with the depth of its center Y row.

For example, Jasper's vortex at Y15 used roughly `15 * 100 + 96 = 1596` depth. Its image extends into Y16/Y17, while those rows' floors have depths 1600 and 1700. Therefore those later rows can paint over the lower part of the vortex.

Phase 20 adds a `cutscene-front` depth mode for large short-lived world-space effects:

- cutscene world FX: `899900`
- field atmosphere overlay: `900000+`
- HUD/minimap: `1000000+`

The Jasper and Veld vortex commands now use `cutscene-front`, so ordinary floor/wall rows can no longer cut off their lower portion. The persistent Jasper/Veld monster sprites keep their ordinary world depth and map coordinates.

## Generic HEAL log cleanup

Story `HEAL` continues to:

- restore HP/MP
- save as before
- play the heal SE unless silent

The generic log:

`不思議な力で体力が回復した！`

is no longer emitted by default.

Events can still explicitly request text with:

- `message: "..."`
- `log: true` to use the legacy generic line

## Stair / locked-link interaction cleanup

Fixed-map blocked/locked stair links no longer automatically print a reason or execute a warning conversation merely because the player steps onto the tile.

Instead the tile prepares an action button:

- if `blockedEventId` / `lockedEventId` exists, pressing the action runs that conversation/event
- otherwise pressing the action displays the configured `blockedLog` / `lockedLog`

Unlocked contact-driven exits remain automatic.

Random-dungeon stairs also stop automatically printing `階段がある。`; the `次の階へ` action remains available.
